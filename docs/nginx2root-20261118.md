# NGINX2Root remediation, 2026-11-18

## Source change and evidence

The active official nginx services in b1, fs and hk now select
`nginx:1.30.7` instead of `nginx:1.25`. This is the stable fixed release,
rather than the floating mainline latest tag. The policy for Laisky-owned
images is unchanged. Ports, mounts, TLS, authentication and routing are unchanged.

Upstream lists 1.30.7+ / 1.31.9+ as fixed for CVE-2026-123007,
CVE-2026-123633, CVE-2026-121810, CVE-2026-123634 and CVE-2026-113425:
- https://nginx.org/en/security_advisories.html
- https://nginx.org/en/CHANGES
- https://nginx2root.com/
- https://github.com/docker-library/official-images/blob/master/library/nginx

HTTP/2 and HTTP/3 issues require those protocols; the resolver issue has
additional same-name subrequest resolution conditions; the mail issue concerns
mail proxying. Turning off HTTP/2 alone is not a comprehensive fix.
Read-only inspection of the corresponding b1/fs/hk configuration sources found
resolver directives and an explicit HTTP/2 directive in b1/logs.conf. That
does not prove the full resolver exploit conditions or the loaded configuration.
No exploit traffic was sent.

## Validation and deployment boundary

Automatic CI checks YAML syntax only. The retained manual regression test parses
each affected Compose file without interpolating secrets and asserts the image:

```sh
python3 -m unittest discover -s tests -p 'test_nginx_images.py' -v
``` Image smoke tests are local/manual
only, not part of automatic CI. From an isolated development Docker daemon:

```sh
docker pull nginx:1.30.7
docker run --rm --network none nginx:1.30.7 nginx -v
docker run --rm --network none nginx:1.30.7 nginx -t
```

The initial PR qualification already passed these commands in run 44363475737
at head 6ea135c, reporting nginx/1.30.7 and digest
sha256:8a7280c664b1a205092ffea6443299e6d307fe65b6f946b02028fa311c29fd01.
Future qualification is manual, without network or host mounts. This is not a test of production certificates,
includes, DNS, routes or the live configuration. The registry digest appears in
the manual pull output; a version tag is not a digest pin.

No production host was inspected or changed. No service was restarted, recreated
or deployed. Running old containers remain vulnerable until a separately approved
rollout pulls and recreates them. A configuration reload alone does not replace
the vulnerable executable. Before rollout, validate each host's complete nginx
configuration against the new image using read-only staging copies, verify
certificates/module compatibility and record the resolved image digest. After
approved recreation verify the actual binary version and application/TLS health.
Do not roll back to the vulnerable image to resolve compatibility problems.

## Other nginx distributions are not covered by the three image changes

- Active SWAG declarations in b1, hk, racknerd and vultr retain
  `lscr.io/linuxserver/swag:latest`. Upstream package_versions.txt currently
  records nginx 1.30.7-r0, but the latest GitHub release is 5.10.0-ls500 from
  November 14. Source metadata alone does not prove the published registry
  manifest or deployed digest contains the fix. Verify the pulled vendor image's
  actual nginx binary before any authorized SWAG recreate. Do not replace SWAG
  with plain nginx, which would lose certificate-management behavior.
  https://github.com/linuxserver/docker-swag/blob/master/package_versions.txt
- Historical commented nginx examples in home/racknerd remain inactive and must
  not be enabled with their old image versions.
- The historical tengine/Dockerfile builds Tengine 2.3.3. No active Compose
  reference was found. Its fork-specific patch status is unverified; do not
  deploy it on the assumption that an upstream nginx tag fixes it.
- The separately reported Linux kernel privilege-escalation chain is not
  remediated by this image change and requires its own vendor assessment.
